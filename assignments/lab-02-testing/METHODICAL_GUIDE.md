# Методичні вказівки до виконання лабораторної роботи №2

**Тема:** тестування, діагностика та контрольоване доопрацювання клієнтської частини вебзастосунку.

**Мета:** навчитися формулювати поведінкові контракти, реалізовувати компонентні тести та наскрізні E2E-перевірки, діагностувати збої, виправляти їх і підтверджувати відсутність регресій.

**Інструменти:** власний React-застосунок ЛР1 (або погоджений аналог), Vitest, jsdom, React Testing Library, userEvent, Playwright, Browser DevTools, Git.

**Джерело вимог:** активність **«ЛР2. Тестування клієнтської частини вебзастосунку»** у Moodle. Чинне завдання вимагає **щонайменше чотири змістовні компонентні тести, два E2E-сценарії, завершений цикл діагностики та одну перевірку якості**, а також звіт у PDF. Максимум – **16 балів**.

**Навчальні приклади:** [компонентне тестування (Л12)](https://github.com/Aroxed/ui-programming-course/tree/main/examples/lecture-12-component-testing), [E2E і діагностика (Л13)](https://github.com/Aroxed/ui-programming-course/tree/main/examples/lecture-13-e2e-diagnostics), [доступність і продуктивність (Л14)](https://github.com/Aroxed/ui-programming-course/tree/main/examples/lecture-14-ui-quality), [контрольована зміна (Л15)](https://github.com/Aroxed/ui-programming-course/tree/main/examples/lecture-15-maintenance-ai).

## Крок 1. Зафіксуйте початковий стан застосунку

Перед початком тестування запустіть застосунок ЛР1 і перевірте вручну основні маршрути, форми, запити до API й повідомлення про помилки. Збережіть поточну версію:

```bash
git status
git add .
git commit -m "Record baseline before testing"
```

Якщо у робочому дереві є непов'язані зміни, розберіться з ними до створення коміту. Тести повинні виконуватися в середовищі з відомими версіями залежностей та передбачуваними початковими даними.

У `README.md` зафіксуйте команди запуску клієнта, сервера API та умови, потрібні для перевірки. Це дає змогу відтворити помилку на перевіреній базовій версії.

**Контрольна точка:** доступний конкретний Git commit, застосунок запускається за README, відомі URL клієнта й API.

## Крок 2. Перетворіть вимоги на поведінкові контракти

Оберіть чотири суттєві вимоги з ЛР1 і запишіть їх як «передумова – дія – результат».

Приклад для застосунку «Особиста бібліотека»:

| № | Передумова | Дія користувача | Очікуваний результат |
|---|---|---|---|
| 1 | Книги завантажені | Відкрити список | Відображаються назви, посилання й стани |
| 2 | Відкрита форма | Надіслати порожню назву | Повідомлення про помилку, POST відсутній |
| 3 | У формі коректні значення | Створити книгу | Запис збережено, оновлено інтерфейс |
| 4 | API відповідає із затримкою або помилкою | Надіслати форму | Видимий стан очікування або помилки |

Ці контракти визначають, **що спостерігає користувач**, і залишаються актуальними після зміни внутрішньої реалізації компонента.

**Контрольна точка:** кожен тест матиме власний контракт, а очікуваний результат можна перевірити незалежно від назв внутрішніх функцій.

## Крок 3. Налаштуйте засоби компонентного тестування

У корені власного React/Vite-проєкту встановіть необхідні залежності:

```bash
npm install -D vitest jsdom @testing-library/react \
  @testing-library/jest-dom @testing-library/user-event
```

У `vite.config.js` додайте налаштування тестів. Приклад для застосунку, який уже використовує `@vitejs/plugin-react`:

```javascript
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    setupFiles: './src/test-setup.js',
    globals: true
  }
});
```

Створіть `src/test-setup.js`:

```javascript
import '@testing-library/jest-dom/vitest';
```

Додайте скрипти в розділ `scripts` файлу `package.json`:

```json
{
  "test": "vitest",
  "test:run": "vitest run"
}
```

Це фрагмент розділу `scripts`, а не готовий повний `package.json`: збережіть інші залежності та властивості свого проєкту.

Запустіть:

```bash
npm run test:run
```

**Контрольна точка:** Vitest запускається, бачить середовище jsdom і не повідомляє про помилку імпорту з `jest-dom`.

## Крок 4. Перевіряйте інтерфейс через доступні назви й ролі

У компонентних тестах віддавайте перевагу пошуку за семантичними ознаками:

| Потрібний елемент | Рекомендований пошук |
|---|---|
| Кнопка з назвою | `screen.getByRole('button', { name: 'Зберегти' })` |
| Поле з підписом | `screen.getByLabelText('Назва книги')` |
| Повідомлення про помилку | `screen.getByRole('alert')` |
| Елемент, який повинен бути відсутнім | `screen.queryByRole(...)` |
| Елемент, який з'явиться асинхронно | `await screen.findByRole(...)` |

`getBy…` перевіряє поточний стан, `queryBy…` повертає `null` за відсутності елемента, `findBy…` очікує його асинхронної появи. Вибір методу залежить від очікуваної поведінки.

Приклад тесту початкової форми (для компонента із доступним полем «Назва книги»):

```jsx
import { render, screen } from '@testing-library/react';
import { expect, it } from 'vitest';
import BookForm from './BookForm.jsx';

it('показує поле назви й кнопку створення', () => {
  render(<BookForm onCreate={async () => {}} />);

  expect(screen.getByLabelText('Назва книги')).toBeInTheDocument();
  expect(screen.getByRole('button', { name: 'Додати книгу' }))
    .toBeEnabled();
});
```

Фрагмент призначений для власного компонента `BookForm` із методички ЛР1. Назви елементів у тесті повинні збігатися з реальною реалізацією.

## Крок 5. Перевірте валідацію через дії користувача

Використовуйте `userEvent` для введення й натискань:

```jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, it, vi } from 'vitest';
import BookForm from './BookForm.jsx';

it('блокує створення книги з порожньою назвою', async () => {
  const user = userEvent.setup();
  const onCreate = vi.fn();
  render(<BookForm onCreate={onCreate} />);

  await user.click(screen.getByRole('button', { name: 'Додати книгу' }));

  expect(screen.getByRole('alert'))
    .toHaveTextContent('Введіть назву книги й автора.');
  expect(onCreate).not.toHaveBeenCalled();
});
```

Важлива перевірка – **відсутність виклику** `onCreate` за некоректного введення. Вона підтверджує, що помилка не обмежується повідомленням, а справді перешкоджає виконанню операції.

Для іншої предметної області змініть текст, назви полів і перевірюваний контракт відповідно до свого застосунку.

**Контрольна точка:** тест проходить за коректної реалізації та завершується помилкою, якщо видалити перевірку обов'язкових полів.

## Крок 6. Відтворіть асинхронні стани та помилку зовнішнього сервісу

Компонентний тест має контролювати зовнішню залежність. У навчальному прикладі Л12 це сервісна функція `saveTask`, яку замінено тестовим двійником (*mock*).

Приклад побудови контрольованого промісу:

```javascript
let resolveSave;
const onCreate = vi.fn(() => new Promise(resolve => {
  resolveSave = resolve;
}));
```

Таку функцію можна передати в компонент `BookForm`. Спочатку перевіряють, що після натискання кнопка переходить у стан «Збереження…» й блокується. Потім викликають `resolveSave` і перевіряють завершення операції.

Сценарій помилки для цього компонента:

```jsx
it('показує помилку зовнішньої операції', async () => {
  const user = userEvent.setup();
  const onCreate = vi.fn().mockRejectedValue(new Error('network down'));
  render(<BookForm onCreate={onCreate} />);

  await user.type(screen.getByLabelText('Назва книги'), 'Нова книга');
  await user.type(screen.getByLabelText('Автор'), 'Приклад автора');
  await user.type(screen.getByLabelText('Рік видання'), '2024');
  await user.click(screen.getByRole('button', { name: 'Додати книгу' }));

  expect(await screen.findByRole('alert'))
    .toHaveTextContent('Не вдалося зберегти книгу.');
});
```

У цьому тесті потрібні імпорти `render`, `screen`, `userEvent`, `vi`, `it`, `expect` і компонента, як у попередніх прикладах.

Контрольований проміс допомагає тестувати стан очікування без випадкових затримок. Не підміняйте тестовим двійником логіку самої форми: її валідація, керування станом і повідомлення повинні виконуватися реально.

**Контрольна точка:** тести відрізняють успіх, помилку й очікування, а результати повторюються після наступних запусків.

## Крок 7. Установіть Playwright та налаштуйте E2E

У корені проєкту:

```bash
npm install -D @playwright/test
npx playwright install chromium
```

Створіть `playwright.config.js`:

```javascript
import { defineConfig } from '@playwright/test';

export default defineConfig({
  testDir: './tests/e2e',
  use: {
    baseURL: 'http://127.0.0.1:5173',
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure'
  },
  webServer: {
    command: 'npm run dev -- --host 127.0.0.1 --port 5173',
    url: 'http://127.0.0.1:5173',
    reuseExistingServer: !process.env.CI
  }
});
```

Конфігурація розрахована на Vite-проєкт із маршрутизацією. Якщо ваш API запускається окремою командою, забезпечте його запуск до E2E-тестів або додайте контрольоване налаштування відповідного сервера.

До `scripts` у `package.json` додайте:

```json
{
  "test:e2e": "playwright test",
  "test:e2e:ui": "playwright test --ui"
}
```

Запуск:

```bash
npm run test:e2e
```

**Контрольна точка:** Playwright відкриває сторінку власного застосунку, а запуск не залежить від ручного відкриття браузера.

## Крок 8. Реалізуйте завершений успішний E2E-сценарій

Наскрізний тест перевіряє реальну взаємодію браузера, маршрутизації та сервера. Приклад для застосунку бібліотеки:

```javascript
import { test, expect } from '@playwright/test';

test('користувач створює книгу', async ({ page }) => {
  await page.goto('/books/new');

  await page.getByLabel('Назва книги').fill('Нова книга');
  await page.getByLabel('Автор').fill('Приклад автора');
  await page.getByLabel('Рік видання').fill('2024');

  await page.getByRole('button', { name: 'Додати книгу' }).click();

  await expect(page.getByText('Нова книга')).toBeVisible();
});
```

У цьому варіанті перевіряється маршрут із методички ЛР1: після успішного створення `BookCreatePage` виконує перехід на `/books`, а `BookListPage` завантажує новий список із сервера. Перед запуском E2E переконайтеся, що тестовий API книг існує, має передбачуваний початковий стан і приймає поля `title`, `author`, `year`, `status`. Якщо індивідуальний застосунок використовує іншу навігацію, скоригуйте тест відповідно до його контракту. Перевірте також фактичний HTTP-запит:

```javascript
const responsePromise = page.waitForResponse(response =>
  response.url().endsWith('/books') &&
  response.request().method() === 'POST'
);

await page.getByRole('button', { name: 'Додати книгу' }).click();

const response = await responsePromise;
expect(response.status()).toBe(201);
```

Варіант із `201` підходить для API, який використовує цей код успішного створення. Пристрій API може повертати інший документований код – тест повинен перевіряти контракт вашого сервера. Очікування `waitForResponse` потрібно створити **до натискання кнопки**.

Наведені два фрагменти ілюструють частини одного сценарію. У власному тесті натискання виконують один раз: створіть `responsePromise` до натискання, виконайте дію, дочекайтеся HTTP-відповіді й лише потім перевірте появу запису у списку. Якщо API повертає не `201`, а інший документований код успіху, перевіряйте саме його.

## Крок 9. Реалізуйте альтернативний або негативний E2E-сценарій

Перевірте, що некоректне введення не призводить до серверного запиту:

```javascript
test('порожня назва блокує створення', async ({ page }) => {
  const postRequests = [];

  page.on('request', request => {
    if (request.method() === 'POST' &&
        request.url().endsWith('/books')) {
      postRequests.push(request);
    }
  });

  await page.goto('/books/new');
  await page.getByRole('button', { name: 'Додати книгу' }).click();

  await expect(page.getByRole('alert'))
    .toHaveText('Введіть назву книги й автора.');
  expect(postRequests).toHaveLength(0);
});
```

Другим E2E-сценарієм може бути також: відсутній запис, відмова API, помилка авторизації або коректне відновлення після збою. Обирайте ті випадки, які реально можливі у вашій предметній області.

## Крок 10. Зробіть початкові дані відтворюваними

Під час E2E важливо визначити, які записи вже існують і як їх скинути. У навчальному сервері Л13 перед тестом викликається спеціальний маршрут:

```javascript
test.beforeEach(async ({ request }) => {
  const response = await request.post('/api/reset');
  expect(response.status()).toBe(204);
});
```

У вашому API такого маршруту може не бути. Використовуйте окрему тестову базу, скрипт початкового наповнення (*seed*), підготовку через API або інший відтворюваний механізм. Скидання тестових даних не повинно впливати на реальні дані користувачів.

Перевірте: два послідовні запуски тестового набору починаються з однакового стану й дають однакові результати.

## Крок 11. Проведіть один повний цикл діагностики

Оберіть реальну помилку або контрольовано внесіть невеликий дефект в окремому коміті. Дотримуйтеся послідовності:

```text
Порушений сценарій
    ↓
Тест, що відтворює збій
    ↓
Повідомлення, Console, Network або Playwright trace
    ↓
Гіпотеза щодо причини
    ↓
Перевірка гіпотези
    ↓
Мінімальне виправлення
    ↓
Повторні тести
```

Приклад: форма двічі надсилає POST під час подвійного натискання. Збережіть послідовність запитів у Network, знайдіть причину у стані `saving` та виправте керування кнопкою. Потім підтвердьте результат повторним тестом.

Для дослідження Playwright trace:

```bash
npx playwright show-trace path/to/trace.zip
```

Цю команду використовуйте з реальним шляхом до створеного файла. Якщо trace відсутній, спочатку відтворіть збій зі збереженням діагностичних артефактів.

**Контрольна точка:** є чіткий доказ причини, мінімальний Git diff і результат перевірки після виправлення.

Запишіть умову перевірки, спостереження і висновок. Це має бути фактичне дослідження, а не перелік невиконаних рекомендацій.

## Крок 13. Оформіть README та звіт у PDF

README забезпечує відтворення запуску без додаткових пояснень:

```text
Назва та призначення
Вимоги до середовища
Встановлення залежностей
Запуск застосунку та API
Компонентні тести
E2E-тести й підготовка даних
Відомі обмеження
```

До короткого PDF-звіту включіть:

1. Чотири поведінкові контракти.
2. Перелік компонентних тестів і два E2E-сценарії з поясненням їхньої ролі.
3. Діагностичний випадок: симптом, докази, причина, виправлення.
4. Git diff або посилання на коміти з виправленням.
5. Результати повного повторного запуску тестів.
6. Одну перевірку якості та висновок.

У звіті потрібні докази й пояснення. Повні списки вихідного коду залишаються в репозиторії. Для діагностики можна додати посилання на trace, скриншот або короткий фрагмент журналу.

| Проблема | Причина | Рекомендована дія |
|---|---|---|
| Компонентний тест шукає випадковий CSS-клас | Прив'язка до структури DOM | Використати роль, підпис або доступну назву |
| Скрізь застосовується `findBy` | Невизначена модель часу | Обрати `getBy`, `queryBy` чи `findBy` за умовою |
| Тест проходить лише окремо | Спільні дані або стан | Забезпечити незалежні підготовку й очищення тестового середовища |
| Очікування через довільний timeout | Не задана умова завершення | Очікувати конкретний стан, URL чи відповідь |
| Тест перевіряє внутрішній виклик | Не визначено користувацький контракт | Перевіряти спостережуваний результат |
| Виправили тест, але помилка залишилась | Немає діагностики причини | Перевірити trace, Console, Network, код |
| Після виправлення не запустили всі тести | Можлива регресія | Повторити повний набір |
| У звіті лише скриншоти | Відсутні докази причинно-наслідкового зв'язку | Додати інтерпретацію, коміт, результати тестів |
