# Розрахунково-графічна робота

**16 балів**

## Тема

Розроблення індивідуального мобільного, кросплатформеного або настільного застосунку.

## Мета

Поглибити практичні навички проєктування і реалізації завершеного інтерфейсу користувача з використанням компонентного підходу, стану, подій, навігації, даних і можливостей обраної платформи. Результатом має бути працездатний застосунок, який студент може запустити, продемонструвати, пояснити та змінити під час захисту.

## Допустимі технології

- React Native;
- Flutter;
- Electron;
- нативний Android (Kotlin / Jetpack Compose);
- інша технологія – після погодження з викладачем.

Технологія має відповідати задачі. Сам факт використання певного фреймворку не є перевагою під час оцінювання.

## Загальне завдання

За своїм варіантом розробіть невеликий, але завершений застосунок з інтерфейсом користувача. Він повинен підтримувати щонайменше **три завершені сценарії користувача**.

Приклади сценаріїв:

- список → деталі → зміна статусу;
- створити → перевірити введення → зберегти;
- викликати платформну можливість → отримати результат → відобразити його;
- відкрити локальний файл → змінити дані → експортувати результат.

## Обов'язкові вимоги

1. **Компонентна структура.** Інтерфейс поділено на логічні компоненти, віджети або Composable-функції.
2. **Стан і події.** Стан реально змінюється внаслідок дій користувача і впливає на відображення.
3. **Навігація.** Є щонайменше два змістовні екрани/представлення або інша явна структура навігації.
4. **Дані.** Використовується локальне сховище, файлова система, SQLite, інша локальна база даних, HTTP API або інше погоджене джерело.
5. **Зміна даних.** Користувач може створити, змінити, видалити або інакше змістовно модифікувати дані.
6. **Валідація.** Некоректне введення не приводить до виконання операції без пояснення користувачу.
7. **Платформна можливість.** Реалізовано щонайменше одну реальну інтеграцію: камеру або вибір зображень, геолокацію, сповіщення, системне надсилання, дозволи, системні діалоги вибору файлів, меню застосунку, буфер обміну, системне сховище або іншу погоджену можливість.
8. **Стани виконання.** Оброблено релевантні стани порожнього результату, завантаження, помилки, скасування, відмови в дозволі та недоступності функції.
9. **Перевірка.** Перед захистом перевірено не менше трьох основних користувацьких сценаріїв.

РГР не вважається завершеною, якщо це набір статичних екранів без стану й даних, копія навчального прикладу лише зі зміненими текстами чи кольорами або якщо заявлена платформна можливість імітується замість роботи з реальним API чи можливістю середовища.

## Вимоги до репозиторію

- власні вихідні файли, конфігурація та файл фіксації версій залежностей;
- без каталогів `node_modules` і `build/dist`, образів емуляторів, секретів та ключів API;
- осмислені проміжні коміти;
- README з вимогами до середовища, встановленням і точними командами запуску.
